# The icon seam

This is a documentation seam, not a dependency. Nothing in this package imports
the ERP's icon registry, and nothing here generates one. When the ERP lane's
icon work (DIB-ICONS-1) lands in `hh`, the icon package inside the design system
adopts the registry below as-is: the same libraries, the same id scheme, the
same format, so one icon system serves every shell.

Until then, the only icons in this package are the five state marks in
`../state-icons.ts`: hand-drawn path geometry on the house 24 grid, held to the
same non-geometry rule the registry holds its entries to.

## The registry format (DIB-ICONS-1, as generated by the ERP's import pipeline)

The generated module is `app/src/_icon-registry.ts` in the ERP tree. Its shape:

```ts
import type { TileIcon } from './_tile-icons.js';

export const ICON_REGISTRY: Readonly<Record<string, TileIcon>> = Object.freeze({
  'lucide:badge-check': Object.freeze({ paths: ['...'] }),
  'pencil:search': Object.freeze({ paths: ['...'] }),
});
```

- **One entry is one icon**: `paths`, an array of SVG path `d` strings, drawn in
  document order. The registry carries no attributes at all. Stroke width, caps,
  joins and `currentColor` are render-time concerns: 24x24 viewBox, stroke 2,
  round caps and joins, one visual weight across the system.
- **Ids are namespaced by source**: `lucide:<name>` from the vendored
  lucide-static tree, `pencil:<name>` from the vendored Penpot controls. The
  libraries are vendored read only, with VERSION, LICENCE and a sha256 manifest
  beside each tree; nothing is fetched at runtime or build time.
- **The fallback-to-module-default rule**: a consumer asks for an id it does not
  find and it still gets an icon, never a codepoint and never an empty box: the
  module's neutral default (the ERP's `_fallback` square, exported under
  `FALLBACK_ICON_ID`). An unmapped id is visible to whoever added it without
  ever being illegible to the person using the screen. Mapping a specific route
  or tile to its default icon is the consumer module's concern, not the
  registry's; Colton's approved defaults per unit and module from checkpoint A
  live in the ERP's DEFAULTS-PROPOSAL, and the one recorded substitution there
  (the runtime hide control maps to `lucide:eye-off` rather than `pencil:hide`)
  is likewise a mapping entry, not a gap in the tree.
- **The non-geometry gate**: the import REJECTS anything that is not path
  geometry (a script, an event attribute, a style, an external reference, an
  embedded image, an animation element), naming the offending file. The same
  reject list holds over the generated registry: its body may be nothing but
  path data strings, identifiers and the frozen record syntax. This package's
  `test/kits.test.mjs` holds `state-icons.ts` to the same list.
- **The idempotence gate**: re-running the import over unchanged trees
  reproduces the registry's bytes exactly. Key order is deterministic (the
  lucide block, then the pencil block, alphabetical within each), so a
  regenerated registry that diffs is a real change, never churn.

## What this package promises

- `state-icons.ts` stays path-data-only and stays on the 24 grid at stroke 2,
  so every mark here can move into a registry entry unchanged.
- When the icon package lands, its registry is the generated `_icon-registry.ts`
  format above, generated by an import pipeline with both gates, from the same
  two vendored libraries under the same id scheme. Consumers resolve icons by id
  through a `tileIcon(id)`-shaped accessor that cannot return undefined and
  cannot return text.
- No code in this package imports from the ERP tree, and none will: the seam is
  the format, not a module path.
