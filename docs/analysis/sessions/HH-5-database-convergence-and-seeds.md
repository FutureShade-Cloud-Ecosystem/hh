# HH-5: database convergence, data migration scripts, and seed datasets

Goal: put HardscapeOS and the `hh` core on one org database on the platform, with rehearsed migration scripts, anonymised seed datasets for previews, and a proven rollback, so a role can move to a new micro-app while the rest of the yard keeps working in the ERP.
Preconditions: HH-3 (core with the additive schema, passing the ERP's own integration suite against it); **S0** complete (Managed Postgres on the platform, with the `dibbits` org database provisioned); **S2** complete (Appwrite identity, so `core` verifies real JWKS tokens rather than the test-generated keys HH-3 ran on); the HardscapeOS staging droplet's apply script and environment file exist as described in `analysis/hardscapeos-inventory.md` section 20 (read, never edited by this session). Until S0 and S2 exist, HH-3 and HH-4 proceed on a preview database with test keys and this session waits.
Position relative to the ERP cutover session: upstream, and it is the pivot every role move stands on. HardscapeOS keeps its code, its deploy workflow and its release cadence; only its database connection target changes, by a configuration change made by the person who operates that droplet, with the previous target kept warm for rollback. This is the one step of the path that touches the in-flight delivery's environment, and it touches configuration only.
Harness: claude for HH-5.1, HH-5.3 and HH-5.6 (data movement, rollback proof, and an implementation repository that must hold configuration by reference and no credential); kimi or kilo for HH-5.2, HH-5.4 and HH-5.5. Integrator and verifier on Claude.

Lanes (parallel unless marked):
- HH-5.1 Rehearsed move of the ERP database
  Scope: a script that dumps the HardscapeOS database from its current Postgres (major version per `hardscapeos_dibbits/docker-compose.yml`), restores it into the platform org database (the shape's major version), applies `core`'s additive migrations, runs the ERP's integration suite against it, and records checksums per table before and after. The rehearsal runs against a restored copy repeatedly until it is boring; the real move is the same script with two connection strings.
  Touches: `hh/core/db/move/` (scripts and the runbook), `hh/docs/runbooks/db-convergence.md`.
  Acceptance: row counts and per-table checksums match after restore; the ERP integration suite and `core`'s suite both pass on the restored copy; `GATE-5c` (stock reconciles, no negative) passes on the moved data; the runbook names the rollback (repoint the ERP to the warm previous target) and it is rehearsed once.
  Prompt: "Write and rehearse the move of the HardscapeOS database onto the platform org database: dump, restore across the Postgres major version, apply `core`'s additive migrations, verify per-table checksums and row counts, run both integration suites. Write the runbook with an explicit rollback and rehearse the rollback too. Never edit `hardscapeos_dibbits`; the ERP's connection change is a configuration step in the runbook for the droplet's operator. No em or en dashes; no dates."

- HH-5.2 HH Pro data migration
  Scope: HH Pro holds no production data (`analysis/hhpro-inventory.md` section 11: one seeded account, state per browser). The migration is therefore a fixture translator, not a data move: `src/core/data/scenario.ts` and `demo-seed.json` become tenant seed rows (`plan`, `plan_line`, `customer_quote`, `tenant_user`) in the shapes `analysis/domain-map.md` section 5.4 gives, priced through `core`'s pricing module rather than the simulator so the numbers cannot drift from what the product would compute (the rule in `hh_pro_dibbits/CLAUDE.md`, "seeded demo data is priced through the real ERP engine").
  Touches: `hh/core/db/seed/tenant-demo.sql` and its generator under `hh/scripts/`.
  Acceptance: the generated scenario exercises every stage rule (a clean plan that can skip the quote desk, one with a special-order line that cannot, one with no date, an empty draft, one project with plans in three stages); a test replays the HH Pro board-flow test (`src/core/__tests__/board-flow.test.ts`) against `core` over this seed.
  Prompt: "Translate HH Pro's scenario and demo seed (`hh_pro_dibbits/src/core/data/`) into tenant seed rows for `core`, priced through `core`'s pricing module, and port the board-flow test to run against the seeded core. HH Pro has no production data to move; say so in the README. No em or en dashes; no dates."

- HH-5.3 Anonymised seed datasets for previews
  Scope: `db/seed/demo.sql` (the manifest's seed) built from the ERP's additive `demoseed` (`hardscapeos_dibbits/backend/cmd/demoseed`, plan-by-default, deterministic ids, `ON CONFLICT DO NOTHING`) plus HH-5.2's tenant rows; an anonymiser that produces a preview dataset from a production restore with names, contacts, addresses and card metadata replaced deterministically and every credential column nulled, verified by a scan that no real email or phone survives.
  Touches: `hh/core/db/seed/`, `hh/scripts/anonymise/`.
  Acceptance: `fb preview` boots a branch preview from `demo.sql` alone; the anonymiser's scan passes; the deterministic ids survive a second run with `created=0`.
  Prompt: "Build `db/seed/demo.sql` from the ERP's additive demoseed plus the tenant seed, and an anonymiser that turns a production restore into a preview dataset with every personal field replaced deterministically and every secret column nulled. Prove the preview boots from the seed alone. No em or en dashes; no dates."

- HH-5.4 Cutover readiness checks as code
  Scope: the checks HH-11 will run per role, written now: an org-database health probe with the live ping semantics of `/healthz` (`analysis/hardscapeos-inventory.md` section 20), a per-role read-only switch in `core` (a role's writes refused with a sentence naming the new app), and the reconciliation queries (stock drift, journal balance, AR subledger tie) as a single `fb`-runnable report.
  Touches: `hh/core/internal/cutover/` (new), `hh/scripts/readiness/`.
  Acceptance: the report runs green against the converged database; the read-only switch is covered by the RBAC sweep (a switched role gets a 403 with the naming sentence on every mutating route).
  Prompt: "Write the cutover readiness report and the per-role read-only switch in `core`. The report reuses the ERP's whole-database invariant queries; the switch refuses writes for a switched role with a sentence naming the app that now owns the work, and the RBAC sweep must cover it. No em or en dashes; no dates."

- HH-5.5 Per-tour seed slices
  Scope: each walkthrough ships the data it needs rather than hunting for a good example at demonstration time, so `core/db/seed/tours/` gains one slice per tour named by the definition that declares it (HH-4.7): a contractor plan at the stage its tour opens on, a priced dealer quote ready to convert, a pick list short enough to work on a phone, a run with stops. Slices are additive over `db/seed/demo.sql` from HH-5.3, carry deterministic ids in their own namespace prefix under the rule this session's integrator already applies to the tenant generator, are applied on tour start and reverted on tour end so one walkthrough cannot contaminate the next, and are priced through `core`'s pricing module rather than written by hand, which is the rule HH-5.2 carries from `hh_pro_dibbits/CLAUDE.md` ("seeded demo data is priced through the real ERP engine").
  Touches: `hh/core/db/seed/tours/`, `hh/scripts/seed-slice/`.
  Acceptance: every slice applies over the demo seed and reverts cleanly twice in a row with identical ids and identical checksums; a slice carries no personal data and passes HH-5.3's anonymiser scan; a slice that seeds a card past the first stage also seeds the supplier artifacts behind it, the internal-consistency rule in `hh_pro_dibbits/CLAUDE.md` ("if you add a seeded card in a later stage, seed its artifacts too"); a tour whose slice fails to apply refuses to start rather than opening on the wrong data.
  Prompt: "Build the per-tour seed slices under `core/db/seed/tours/` and their generator: one slice per tour definition in `statecharts/tours`, additive over `db/seed/demo.sql`, deterministic ids in a per-tour namespace prefix, applied on tour start and reverted on tour end, priced through `core`'s pricing module and never by hand. A card seeded past the first stage carries its supplier artifacts. A slice that cannot apply stops its tour. No em or en dashes; no dates."

- HH-5.6 `impl-hh-demo` from the implementation model
  Scope: the demo org is a client, not a special case, so it gets an implementation repository built from the client implementation model in `context/FUTURESHADE-CONTEXT.md` section 5: `PRODUCT_TAG` pinned to the `hh` tag under test, the org manifest with every capability the product can expose switched on, configuration only (brand `hh`, terms, feature flags, integration endpoints pointed at stubs, payments in test mode), the seed pointed at the demo scenario from HH-5.2 and the tour slices from HH-5.5, secrets by reference alone, the sandbox template, and an `OVERLAYS.md` ledger that starts empty and is meant to stay that way, because anything the demo needs that the product cannot express by configuration is a product capability flag rather than a patch. Nothing in this lane touches the `dibbits` org, the ERP's environment or any precondition of this session.
  Touches: the `impl-hh-demo` repository (`PRODUCT_TAG`, `manifest.yaml`, `config/`, `seed/`, `OVERLAYS.md`, `docs/`); `hh/docs/runbooks/impl-hh-demo.md` records what the implementation pins and how it is upgraded.
  Acceptance: `fb check` passes for the implementation; a test diffs the product's capability list against the demo manifest so a capability added to `hh` fails the demo until someone decides whether the demo shows it; no credential value appears anywhere in the repository, only Infisical paths, proven by a scan; `OVERLAYS.md` is empty and a test fails if it is not; `fb upgrade` runs against a branch preview restored from the demo seed and opens its pull request. Guardrail, stubbed integrations, checked where they are configured: every integration endpoint in the manifest points at a stub, messaging is routed to a sink, payments are in test mode, and a test over the manifest fails when any of the three is set to a live target, so the demo org cannot be provisioned in HH-7.5 with a live integration behind it.
  Prompt: "Create the `impl-hh-demo` implementation repository per `context/FUTURESHADE-CONTEXT.md` section 5: `PRODUCT_TAG`, an org manifest with every capability on, configuration only (brand `hh`, stubs for every outbound integration, payments in test mode), the seed pointed at the demo scenario and the tour slices, secrets by reference, and an empty `OVERLAYS.md`. Add a test that fails when a new product capability is undeclared here and a scan that fails on any credential value. Prove `fb upgrade` runs against a preview restored from the demo seed. No em or en dashes; no dates."

Integrator: 5.1 first; 5.2 and 5.3 together (5.3 consumes 5.2's rows; take 5.2's ids as canonical); 5.5 after 5.3, since a slice is additive over the demo seed; 5.4 last. 5.6 touches no database and no shared file, so it runs beside 5.1 from the start. Expected conflict: seed ids between the ERP demoseed and the tenant seed; both are deterministic, so the resolution is a namespace prefix in the tenant generator, extended to one prefix per tour slice. Second expected conflict: the demo manifest in 5.6 and the seed path in 5.5 name the same slices; the definitions in `statecharts/tours` are the single list and both read it.
Verifier: both integration suites green on the moved database; checksums match; `GATE-5a`, `GATE-5b`, `GATE-5c` green on the moved data; preview boots from the seed; anonymiser scan clean over the demo seed and every tour slice; each tour slice applies and reverts twice with identical checksums; `fb check` green for `impl-hh-demo` with an empty `OVERLAYS.md` and a clean credential scan; the readiness report green; the rollback rehearsal recorded in the runbook with its result.
Human checkpoints: start (Colton confirms the maintenance window is the droplet operator's to arrange and that the previous database stays warm; confirms who runs the connection change); mid (none); end (Colton signs off the runbook; the droplet operator performs the connection change from the runbook and both applications are observed writing one database).
Exit test: HardscapeOS is serving from the platform org database with its own suite green, `core` is serving the same database with its suite green, the rollback has been rehearsed, a preview boots from `demo.sql`, every tour slice applies over that preview and reverts leaving identical checksums, `impl-hh-demo` exists with every product capability switched on and no overlay, and the readiness report is green.
Produces: the convergence runbook and scripts; `db/seed/demo.sql`; the per-tour seed slices and their generator; the anonymiser; the `impl-hh-demo` implementation repository and its runbook; the readiness report and the per-role read-only switch.
Unlocks: HH-6 (the first role can move because both applications share one database); HH-7.5 (the demo org can be provisioned because its implementation repository exists and its data exists).
