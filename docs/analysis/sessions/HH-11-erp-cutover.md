# HH-11: the ERP cutover

Goal: make `core` the sole writer of the `dibbits` org database, place every HardscapeOS surface read-only for every role, carry the BisTrack parallel-run responsibility into `core`'s `worker`, and close the tracking ledger, so the strangler is complete and the old applications can be retired.
Preconditions: HH-6 through HH-10 (every role in `analysis/role-catalog.yaml` marked moved in the strangler ledger); the HardscapeOS delivery's own last phase (its parallel run with BisTrack and its cutover from BisTrack, `analysis/hardscapeos-inventory.md` section 14.5) is either complete or the sync responsibility has been handed to `core` under the same direction-of-truth data (`backend/internal/bistrack/direction.go`); the readiness report green; the tracking ledger current with the ERP head.
Position relative to the ERP cutover session: the cutover itself. Every session before it moved a role while both applications wrote one database; this session removes the second writer. It sits after the delivery's own BisTrack phase because the `hh` cutover replaces the application over the same data and never the system of record, and doing both in one motion would remove the rollback the parallel run exists to keep.
Harness: claude throughout (this session moves the system of record's write authority). Integrator and verifier on Claude.

Lanes (sequential unless marked):
- HH-11.1 Final tracking reconciliation (sequential, first)
  Scope: the last pass of the tracking lane (HH-3.7): every ERP migration and route above the baseline ported and ledgered; the route-parity diff empty against the ERP head; the ledger closed with a final entry naming the ERP commit it matches.
  Touches: `hh/core/db/PORTED.md`, `hh/core/db/migrations`, `hh/core/api/openapi.yaml`.
  Acceptance: parity diff empty; both integration suites green on the shared database; the ledger's closing entry present.
  Prompt: "Run the tracking lane to completion against the HardscapeOS head: port, ledger, and prove parity. Close the ledger with the commit it matches. Do not modify `hardscapeos_dibbits`. No em or en dashes; no dates."

- HH-11.2 BisTrack responsibility into `worker` (parallel with 11.1 if the delivery's phase is complete; sequential after it otherwise)
  Scope: the `bistrack` module's pull and push connector seam, direction-of-truth data and discrepancy tables run as a `worker` job in `core`; if the parallel run is still open, the push keeps BisTrack current from `core`'s writes exactly as the ERP's module intended; if it is closed, the module carries as read-only archive tooling and the read-only archive sign-off (`docs/legacy/ANOMALIES.md` BT-A-022) is recorded.
  Touches: `hh/core/internal/bistrack`, `hh/core/cmd/core` (worker registration).
  Acceptance: the module's structural test still passes; the health token reports the sync state from `core`; if live, one round trip of each entity is observed and the discrepancy table is empty.
  Prompt: "Move the BisTrack sync responsibility into `core`'s `worker` under the module's frozen connector seam and direction data, live if the parallel run is open and archival if it is closed. The signatures do not change. No credential is read; configuration arrives as environment. No em or en dashes; no dates."

- HH-11.3 The global read-only switch and the write-authority handover (sequential)
  Scope: the per-role switch from HH-5.4 raised to every role, so every HardscapeOS write returns the naming sentence; the ERP's `serve` process left running read-only for the retention window the runbook names; `core`'s `serve` and `worker` the only writers; the outbox drained once from the ERP side and then only from `core`; the readiness report run before and after; the rollback (flip the switch back, both applications write again) rehearsed and then retired.
  Touches: `hh/docs/runbooks/erp-cutover.md`, `hh/core/internal/cutover/`.
  Acceptance: the readiness report green before and after; the RBAC sweep proves every ERP mutating route returns the naming sentence for every role; stock drift zero, journals balanced, AR tied; the ERP's own gate suite, run read-only, still passes its read legs.
  Prompt: "Execute the ERP cutover from the runbook: global read-only in HardscapeOS with the naming sentence, `core` as sole writer, one final outbox drain, the readiness report before and after, the rollback rehearsed first. Never edit `hardscapeos_dibbits`; the switch is `core`'s and the ERP's read-only state is a configuration change made by its operator. No em or en dashes; no dates."

- HH-11.4 Observation and the strangler ledger's close (sequential, last)
  Scope: the observation checklist per role (one complete job per micro-app performed by a real person and reconciled), the ledger's final state, the ADR amendments the cutover forced, and the list of ERP surfaces now eligible for decommission in HH-12.
  Touches: `hh/docs/runbooks/strangler-ledger.md`, `hh/docs/adr/`.
  Acceptance: every role's observation row signed; the decommission list names every ERP entry and unit with the session that replaced it.
  Prompt: "Close the strangler ledger: one observed job per micro-app, signed; record the ADR amendments; produce the decommission list for HH-12 with the replacing session per surface. No em or en dashes; no dates."

- HH-11.3a The walkthroughs as release checks (runs twice inside 11.3's order, before the switch and after the handover)
  Scope: the three tours (counter-to-yard, dispatch-to-delivery, contractor-to-homeowner) run as release checks before the global read-only switch and again after the write-authority handover, against the `dibbits` staging restore rather than against `hh-demo`, because a release check has to exercise the data shape of the org that is about to change and `hh-demo` is a different org with different rows. The restore is the anonymised one from HH-5.3, so the check never runs against the client's real data and never adds a writer to the production org. Each run applies the tour's seed slice inside a tenant reserved for checks and reverts it afterwards, so the environment is identical before and after. The tour guards are the pass condition: a failed guard stops the cutover step it gates, which is what makes this a gate rather than a report.
  Touches: `hh/docs/runbooks/erp-cutover.md` (the release-check gate in the order of operations), `hh/scripts/tour-record/` (the release-check mode), `hh/statecharts/tours/**` (guards only where a cutover state differs from the demo's).
  Acceptance: all three tours green against the `dibbits` staging restore before the read-only switch and again after the handover; a deliberately broken guard is rehearsed once and proves the step stops rather than warns; the runs leave no row behind, with the reserved tenant's checksums identical before and after; no tour runs against the production org, proven by the connection target recorded in each run's report.
  Prompt: "Add the release-check mode to `scripts/tour-record` and wire the three tours into `docs/runbooks/erp-cutover.md` as a gate, run before the global read-only switch and again after the write-authority handover, against the anonymised `dibbits` staging restore and never against the production org. Each run applies its seed slice in a reserved tenant and reverts it. A failed guard stops the step. Rehearse a deliberately broken guard once to prove the gate stops. No em or en dashes; no dates."

Integrator: strictly sequential; no parallel lanes except 11.2 when the delivery's phase is already complete. 11.3a carries a letter rather than the next number because lane numbers are read as run order everywhere else in the path and this lane is the exception: it executes twice inside 11.3's order, before the switch and after the handover; the runbook, never the lane number, is the order. No merge conflicts expected; the risk is ordering, and the runbook is the order.
