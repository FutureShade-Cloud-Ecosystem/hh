- HH-2.3 The OpenAPI document, tenant API first
  Scope: author `core/api/openapi.yaml`. Part one, the tenant API: every `/api/portal/v1` route in `hardscapeos_dibbits/backend/internal/portal/*.go` (about fifty, listed in `analysis/hardscapeos-inventory.md` section 12), renamed under `/api/v1/tenant/`, with request and response schemas taken from the Go structs and cross-checked against `hh_pro_dibbits/src/core/supplier/adapters/erp-wire.ts` and the recorded fixtures under `hh_pro_dibbits/src/core/supplier/__tests__/fixtures-live/`. Part two, the staff API: one path group per ERP module from each `RegisterRoutes`, schemas from `model.go`, with the `X-Org` header, cursor pagination (`cursor`, `limit`, `next_cursor`) replacing offset on every list, and a `role` extension on every operation naming the gate. Part two also resolves D6: order resources carry the one canonical core id as `id`, the contractor-side id as the alias `legacy_contractor_id` for the mapping period, and every deep link `fb://hh/order/<id>` carries the canonical id only; and D4: the operator reads and writes the launcher section needs (platform key roster, the write-only dealer credential route, the per-account usage counter) are org-scoped endpoints in the staff API. Part two also resolves D7 to D12 (`analysis/DECISIONS.md`): one canonical `order` aggregate with the contractor's board card as the read projection `OrderCard`, defined with an explicit field map and a documented, total state map from dealer order states to the contractor vocabulary (D7); two quote resources, `dealer_quote` (priced by `core` under D1, carrying `valid_until`) and `customer_quote` (carrying the acceptance artifact and the magic-link token), sharing the `quote_line` shape and nothing else, with no `kind` field (D8); the ERP invoice canonical and the tenant-facing `InvoiceView` exposing lines, tax and holdback totals, balance due and payment history, never subledger internals (D9); `attachment` and the polymorphic `attachment_link` with bytes in Appwrite Storage (D10); one `product_image` model with `swatch_hex` as a fallback attribute (D11); `tenant_brand` under tenant scope, rendered inside the HH Pro frame on customer quotes and the public desk (D12). Part three, the sync surface: `GET /sync/{scope}` and `POST /sync/{scope}` for every scope the manifest declares, with `seq`, tombstones and the conflict envelope.
  Touches: `hh/core/api/openapi.yaml`; `hh/core/api/README.md` recording each route's source path in the ERP.
  Acceptance: the document validates; a script lists every route string registered in `hardscapeos_dibbits/backend/internal` (the same grep `analysis/hardscapeos-inventory.md` section 2.6 used) and every route in the document, and the diff is empty except for routes on an explicit drop list with a reason each; the recorded HH Pro fixtures validate against the tenant schemas; the `OrderCard` state map covers every value in the dealer order status CHECK set and every value in HH Pro's stage union, with no unmapped state on either side (D7); `dealer_quote` and `customer_quote` share only `quote_line` by schema reference (D8).
  Prompt: "Author `core/api/openapi.yaml` for the `hh` core before any Go code exists. Start with the tenant API from `hardscapeos_dibbits/backend/internal/portal` and validate every response schema against the recorded fixtures in `hh_pro_dibbits/src/core/supplier/__tests__/fixtures-live/`; a fixture that does not validate is a finding to record, never a schema to loosen. Then the staff API module by module from every `RegisterRoutes` in `hardscapeos_dibbits/backend/internal`. Then the sync endpoints per scope from `hh/manifest.yaml`. Every list uses cursor pagination. Every operation carries the gate role. Write the route-parity script and make it a test. No em or en dashes; no dates."
