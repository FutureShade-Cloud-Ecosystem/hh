# HH-4: the shared packages

Goal: build the four web packages every micro-app consumes (design system from tokens, auth with device unlock, offline-store with the SQLite and wa-sqlite backends, and the generated api-client) plus the sync statechart with model-based tests as the acceptance gate.
Preconditions: HH-2 (skeleton, manifest, OpenAPI). Runs in parallel with HH-3; the api-client lane regenerates whenever HH-3.4 changes the document.
Position relative to the ERP cutover session: upstream. Pure library work; nothing deployed.
Harness: claude for HH-4.3, HH-4.4 and HH-4.7 (offline-store and the statecharts are the correctness core of every offline and every walkthrough claim) and HH-4.2 (auth); kimi or kilo for HH-4.1, HH-4.5 and HH-4.6. Integrator and verifier on Claude.

Lanes (parallel unless marked):
- HH-4.1 Design system from tokens
  Scope: `web/packages/design-system`: one `tokens.css` with the base tokens for internal apps and two brand overrides (`hh-pro` for the standalone shell, and the contractor override HH Pro's `--cbrand-*` layer expresses, applied only on the public proposal); the five kits the catalog uses (`scan-and-confirm`, `list-detail`, `guided-flow`, `dashboard`, `inbox`) as Lit components over Ionic primitives; the five states designed once per pattern (empty, loading, offline, conflict, error); the disabled-must-look-disabled rule and the colour-never-alone rule carried from `hh_pro_dibbits/CLAUDE.md`; the measured-contrast gate carried from both repositories (`hh_pro_dibbits/scripts/contrast-probe.mjs`, `hardscapeos_dibbits/app/scripts/contrast-check.mjs`); the phantom-token gate from `hardscapeos_dibbits/app/src/_theme-tokens.test.mjs`; Penpot component names one-to-one with element names.
  Touches: `hh/web/packages/design-system/**`.
  Acceptance: every token pair used by a kit clears the measured contrast threshold in a real browser, three ways as the ERP's `tokens.css` header describes; no phantom token; the empty, offline and conflict states render for each kit in a storybook-style harness Grant can open.
  Prompt: "Build `web/packages/design-system` per `context/FUTURESHADE-CONTEXT.md` sections 3 and 4.5. Merge `hardscapeos_dibbits/app/src/styles/tokens.css` and `hh_pro_dibbits/src/ui/styles/theme.css` into one base vocabulary plus per-brand overrides; keep both repositories' measured-contrast gates and the phantom-token gate as tests; implement the five kits and the five states. Colour never encodes state alone; disabled controls change colour, not opacity. No em or en dashes; no dates."

- HH-4.2 Auth with device unlock
  Scope: `web/packages/auth`: platform login through Appwrite Auth, JWT held in memory and mirrored to a throw-safe storage shim (carry `hardscapeos_dibbits/app/src/api.ts`'s shim rationale), `X-Org` on every request, cached session plus device unlock (PIN or biometric) for shared devices, the unlocked user stamped into an audit header, and the never-ship-a-role-picker-the-server-cannot-enforce rule (`hh_pro_dibbits/src/core/supplier/port.ts:71-77`).
  Touches: `hh/web/packages/auth/**`.
  Acceptance: a token never appears in `localStorage`; the storage shim degrades to memory when the accessor throws; the unlock flow is tested with a fake credential provider; a request without `X-Org` is refused by the client before it leaves.
  Prompt: "Build `web/packages/auth`: Appwrite login, in-memory token custody with a throw-safe session mirror, `X-Org` on every call, cached session plus device unlock for shared devices with the unlocked user recorded, and no client-side role rendering that the server does not enforce. No em or en dashes; no dates."

- HH-4.3 Offline-store, two backends
  Scope: `web/packages/offline-store`: the local schema from context 4.5 (projection tables per declared scope, `outbox(id, op, payload, scope, created_at, attempts, status, error)`, `sync_state(scope, last_seq, last_pull_at)`, `attachments_queue`), a SQLite backend for Tauri and a wa-sqlite-on-OPFS backend for the PWA with an IndexedDB read-cache-only fallback, the outbox contract carried from `hardscapeos_dibbits/app/src/dispatch-logic.ts:214-276` (client-minted ids, success removes the entry, retry only on no response or a 5xx, the label never says done), the projection integrity rules carried from `hh_pro_dibbits/src/core/stores/persistence.ts` (all-or-nothing restore, a stashed corrupt backup, a debounced writer with an explicit flush), and the single-writer rule carried from `hh_pro_dibbits/src/core/stores/cross-tab.ts` (an echo-proof adopter plus a heartbeat leader lease so one tab runs the sync machine).
  Touches: `hh/web/packages/offline-store/**`.
  Acceptance: one test suite runs against both backends and the fallback; the first-save test is written as a separate file that never calls the flush (the lesson in `hh_pro_dibbits/src/core/__tests__/first-save.test.ts`); a two-tab test proves exactly one leader; the outbox state machine is exhaustively tested.
  Prompt: "Build `web/packages/offline-store` per `context/FUTURESHADE-CONTEXT.md` section 4.5 with a SQLite backend for Tauri, a wa-sqlite OPFS backend for the PWA and an IndexedDB read-cache fallback. Carry the ERP's outbox rules from `hardscapeos_dibbits/app/src/dispatch-logic.ts` and HH Pro's persistence and cross-tab rules from `hh_pro_dibbits/src/core/stores`. One suite must pass on every backend. No em or en dashes; no dates."

- HH-4.6 The `guided-tour` pattern in the design system
  Scope: `web/packages/design-system` gains `guided-tour` as a pattern beside the five states: a step overlay with a spotlight, step copy and one next action; role aware, so the step set a viewer is offered is the set their role can actually reach; skippable and resumable from the step it was left on, with the resume point held in interaction state and never in the outbox, because a walkthrough is not work; usable from every shell (`hh-work`, `hh-field`, `hh-pro` and the public web shell) because it is a pattern over the tokens rather than a feature of one shell. The pattern's next action invokes the same control a real user would press and never a hidden code path, which is the rule HH Pro already holds for its agent tools (`hh_pro_dibbits/src/core/ai/tools.ts`, every mutating tool calls the action a button calls); a step therefore cannot demonstrate something the product will not do. Carries the design-system rules already in this session: colour never encodes state alone, disabled controls change colour rather than fade (`hh_pro_dibbits/CLAUDE.md`), the measured-contrast gate (`hh_pro_dibbits/scripts/contrast-probe.mjs`), and Penpot component names one to one with element names.
  Touches: `hh/web/packages/design-system/**`.
  Acceptance: the pattern renders over each of the five kits in the harness Grant opens, at phone width and at desktop width; the overlay copy over the dimmed backdrop is measured by the same contrast gate as every other pair, not exempted from it; a step whose target control is absent fails loudly rather than spotlighting empty space (the lesson in `hh_pro_dibbits/scripts/capture-guide.mjs`, which fails when a screen it expects is missing); skip and resume are covered; the a11y run at phone width is clean with a step open, with focus held in the step, the page beneath it inert and the step announced.
  Prompt: "Add a `guided-tour` pattern to `web/packages/design-system` beside the five states: spotlight step overlays with copy and one next action, role aware, skippable and resumable, usable from every shell. The next action must invoke the same control a real user presses, never a private path. A step whose target is not on screen fails loudly. The overlay is covered by the measured-contrast gate and the a11y run, with focus trapped and the page beneath inert. No em or en dashes; no dates."

- HH-4.7 The tour statechart convention and its model-based harness
  Scope: `statecharts/tours`: a walkthrough is a statechart, on the same terms as every other definition in this package (no Bun, Node or DOM imports, guards and actions by name, JSON-serialisable so a later Go runtime can interpret it). States are steps, transitions are the viewer's actions or scripted data changes, and every guard asserts that the application reached the expected state before the step advances, which is what makes a tour a check rather than a narration. The convention fixes the machine shape (`ready`, `step`, `done`, with `skipped` and `blocked`), the declared role a tour runs as, and the declared seed slice it needs (HH-5.5); the README states that a tour definition without its model-based test does not ship, which is this package's standing rule. One headless runner in `hh/scripts/tour-record` interprets a definition and emits either a recording with screenshots or a pass or fail report, so the same file drives the demo, the marketing clip and the release check.
  Touches: `hh/statecharts/tours/**`, `hh/statecharts/README.md`, `hh/scripts/tour-record/`.
  Acceptance: the model-based harness walks every reachable path of a sample definition and fails when a guard's target state is absent; the package scan proves no tour definition imports Bun, Node or the DOM; a tour left in `skipped` leaves the application unchanged; the recorder and the release check are proven to be one runner by a test that produces both outputs from one definition; the runner refuses to start when something else is already serving its port and asserts the served title is this repository's own before it drives anything, the rule `hh_pro_dibbits/CLAUDE.md` states as "a gate must know it is grading its own program".
  Prompt: "Write the tour statechart convention in `statecharts/tours` and its model-based test harness, per the statecharts package rules in `context/FUTURESHADE-CONTEXT.md`: steps as states, viewer actions and scripted data changes as transitions, guards asserting the application state, a declared role and a declared seed slice per tour. Definitions import nothing from Bun, Node or the DOM. Build one headless runner in `scripts/tour-record` that emits either a recording or a pass or fail report from the same definition, and make it refuse to run against a server it did not start. No em or en dashes; no dates."
